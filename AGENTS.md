# AGENTS.md

Guidance for coding agents (and humans) that work on Tabernetes. The
[Readme](README.md) explains what Tabernetes is and how it works; this file
holds the decisions, constraints and gotchas behind it that are not obvious
from the code. Read both before you change something.

Tabernetes ("Kubernetes in your tab") is a real Kubernetes control plane
(kube-apiserver, kube-controller-manager, kube-scheduler, kubectl) compiled
to `js/wasm` and running in a browser tab, plus a Docker node image that joins
the cluster over WebRTC. It is the demo on <https://jkroepke.de/tabernetes/>.
It was called "kwasm" until 2026-11-08; old commits, branches and notes use
that name.

## Repository and release

- Tabernetes lived in `tabernetes/` (before that `kwasm/`) of
  [jkroepke/blog](https://github.com/jkroepke/blog). The history up to
  `jkroepke/blog#154` was imported with `git filter-repo`, so `#123` in old
  commit messages was rewritten to `jkroepke/blog#123`.
- The blog does not build Tabernetes anymore. It pins a release
  (`TABERNETES_VERSION` in the `mise.toml` of the blog, bumped by Renovate),
  downloads `tabernetes.tar.gz`, verifies its attestation, unpacks it into
  `assets/tabernetes/` and serves `proxy-sw.js` as `/tabernetes-proxy/sw.js`.
  The shortcode `layouts/_shortcodes/tabernetes.html` and the page
  `content/tabernetes/index.md` stay in the blog. A change of the `data-*`
  contract of `web/src/index.js` therefore needs a change of the shortcode in
  the blog after the release.
- Releases: semantic-release (`.releaserc.json`, commit analyzer only) runs on
  every push to `main` and creates the tag with `GITHUB_TOKEN`, then dispatches
  CI on the tag (a tag pushed with `GITHUB_TOKEN` triggers no workflow, a
  `workflow_dispatch` does; no GitHub App needed); the tag run of CI builds,
  pushes the node image as `<version>` and `latest`, attests and publishes the
  release. PR titles must start with `feat`, `fix`, `chore` or `docs`
  (`pr-check.yaml`); squash merges make the PR title the commit message.
- The release job runs only when the repository variable `RELEASES_ENABLED`
  is `true`. Set it to anything else to merge to `main` without releasing.
- The node image of a release is pinned in the bundle (`TABERNETES_VERSION`
  at build time). Local builds and PRs use `latest`.

## Working rules of the maintainer

- Agents may push to this repository directly; commits here do not need
  Joe's GPG/SSH signature. Only the blog needs signed commits made on Joe's
  Mac.
- No references to Claude or AI in commit messages or PR bodies. The GitHub
  tooling may append a "Generated by Claude Code" footer to a PR body; remove
  it after creating the PR.
- Sign off every commit for the DCO (`git commit -s`), in this repository and
  in the blog.
- Ask before a force push.
- Write docs and comments in plain English (B2 level): short sentences that
  explain the why.

## Architecture decisions (and why)

- **Upstream components, no simulators.** The maintainer wants the normal
  Kubernetes experience. When a tab feature prints events or status, copy the
  upstream kubelet messages (`Pulling`, `Successfully pulled ... Image size`,
  `already present on machine`, `ErrImagePull`, `ImagePullBackOff`, ...) from
  the Kubernetes source instead of inventing text. Readers should recognise
  real kubectl output.
- **One binary.** apiserver, controller-manager, scheduler, kubectl, the shell
  (mvdan.cc/sh) and an in-memory etcd v3 gRPC shim (`k8s/tabernetes/etcdshim`).
  Go `js/wasm` has an in-process fake network (`net.Listen`/`net.Dial` match
  the exact address), so the components talk to each other unchanged. Bind to
  `127.0.0.1`, never `0.0.0.0`.
- **Control plane in a SharedWorker** (`web/src/cluster.js`,
  `k8s/tabernetes/tabs.go`). Every tab joins as node `tab-N` over
  MessagePorts; a Web Lock per tab is its liveness. A closed tab is taken over
  by the others (the `llm` Deployment prefers its tab but is not pinned).
  Without SharedWorker or Web Locks the tab runs the control plane itself.
  Chrome on Android has SharedWorker again since Chrome 148. The worker is
  created with `extendedLifetime` (Chrome 148+), so it outlives the last tab
  by about 30 s and a reload joins the running cluster. `forget` closes it
  with the last tab.
- **Thin tabs** (`k8s/tabernetes/session.go`, `web/src/bridge.js`): with the
  SharedWorker, a tab runs no Go. The shell, kubectl and the kubelet of
  every tab are a session in the worker; the tab keeps xterm, the line
  editing, the built-ins in JS, WebRTC and the workers of its pods (a shared
  worker cannot start workers, so the worker asks the tab to `spawn` one and
  the tab relays its messages). Measured 2026-11-12 against v1.1.0
  (headless Chromium): reload with a running worker 1.4-1.6 s -> 0.2 s to
  the prompt, a further tab 1.5-1.9 s -> 0.2-0.3 s, and each further tab
  ~730 MiB -> ~110 MiB of renderer RSS. Things that are process wide in Go
  stay so: `os.Chdir` for kubectl, `localhost` of port-forward (shared by
  all tabs), and the terminal hooks of moby/term and `kubectl edit`, which
  is why only one `kubectl -t`/`edit` runs at a time (`ownTTY`). Without a
  SharedWorker the tab runs the control plane and one session itself.
- **The kubelet of a tab is like a Virtual Kubelet**: a node for the control
  plane, but no container runtime. Limit of 8 pods per tab (kept on purpose).
- **Real images in a tab run in v86** (32-bit x86 JIT to Wasm, Joe's fork
  [jkroepke/v86](https://github.com/jkroepke/v86), see below),
  one worker per pod, `linux/386` image variants. Chosen over TinyEMU (no JIT,
  last release 2019). Kernel: upstream stable Linux (7.3, a tag of
  `gregkh/linux` pinned by its commit in `vm/Dockerfile`, Renovate bumps both)
  for i386, `tinyconfig` + `vm/kernel.config` with `CONFIG_HIGHMEM4G` (pods
  up to 2 GiB; v86 caps guest RAM at 2 GiB - 128 KiB; without highmem the
  guest used only ~896 MiB). It was Linux 6.8 from Ubuntu's `linux-source`
  until 2026-11-12.
- **PID 1 of the VM is C** (`vm/init/init.c`, static, musl, compiled by
  `zig cc -target x86-linux-musl` from pip in `vm/Dockerfile`; an i386
  Alpine fails on the arm64 CI runners). It was Go until 2026-11-11. Measured
  with the same pod: 77 KB instead of 3.1 MB, 0.2 MiB RSS and 1 thread
  instead of 3.7 MiB and 5, a saved VM state of 17.9 instead of 23.7 MB, and
  the pod starts ~80 ms sooner in the browser. Idle CPU did not change on
  the tickless kernel (Go's sysmon sleeps when nothing runs). Keep it one
  poll loop without threads, and keep the exec protocol of
  `k8s/tabernetes/v86exec.go`. `vm/test` runs init on the host
  (`TABERNETES_INIT_TEST`, no mounts, Linux only) and checks exec, attach,
  stdin acks, ttys and exit codes.
- **v86 is Joe's fork** (since 2026-11-13): jkroepke/v86 is a "hack fork"
  tuned for pods (its `AGENTS.md` lists the changes and how to measure them
  with `tools/pod-bench`). `web/package.json` pins a commit of its branch
  `dist` (`github:jkroepke/v86#<commit>`), which holds only the built npm
  package files (`tools/dist.sh` in the fork makes it), so the build needs
  no Rust or Java. Its version is unique per commit: saved VM states are
  keyed by it, and a state of another v86 build (other CPUID) must not be
  restored. It needs Wasm SIMD (all current browsers). The 9p server calls
  `readInto` of `LayerStorage`: in the worker of a pod, a read-only OPFS
  sync access handle (`layers.js`) reads the file data straight into guest
  memory, and v86 answers the read in the same call; browsers without the
  `read-only` mode keep the Blob reads. Measured against v86 0.5.473
  (2026-11-13, Node.js, `tools/pod-bench` of the fork, main-thread CPU,
  medians of 10 alternating rounds on a busy machine): nginx from `go` to
  HTTP 1500 -> 1040 ms, a static Go binary (start + 20 scrapes) 2810 ->
  1780 ms, glibc text tools 10.1 -> 7.3 s, a JIT-bound shell/gzip/sha256
  job 6.8 -> 6.4 s; sha256sum and AES in OpenSSL 1.7-3x (SHA and AES-NI).
  Since 0.5.75-fork the JIT compiles one page per module: V8 recompiles
  hot modules with TurboFan on background threads, which was ~60 % of the
  CPU of a Spring Boot pod, and its cost grows faster than the module.
  Process CPU (all threads) spring 263 -> 160 s, Go binary 12.5 -> 8.8 s,
  nginx 3.75 -> 2.83 s; peak RSS of spring 1108 -> 770 MiB. 0.5.79-fork
  raises the JIT threshold 200k -> 750k: process CPU nginx 2.83 -> 1.09 s,
  Go binary 8.8 -> 3.1 s. The tab compiles v86.wasm once (`postStart` in
  `vm.js`) and posts the Module with the start message of every pod; a
  shared worker cannot post a Module, so `relay` in `bridge.js` adds it on
  the tab side. A worker that compiles the file itself starts on baseline
  code and V8 optimises the interpreter again (go to `started` 180 -> 70 ms,
  ~0.4 s CPU per pod, headless Chromium). 0.5.80-fork compiles only the
  side of a conditional jump that the interpreter saw run (cold code of a
  module 55 % -> 15-20 %): process CPU spring 134 -> 110 s, glibc 11.9 ->
  9.2 s, Go binary 3.9 -> 3.3 s; nginx compiles almost nothing anymore.
  0.5.81-fork makes memory accesses in JIT code cheaper (one compare for
  the TLB check; a miss leaves the module for the interpreter instead of
  calling a slow path, so V8 keeps guest registers in host registers):
  spring main thread 75.5 -> 59.3 s, process 106.7 -> 76.0 s. 0.5.84-fork
  lets an idle guest sleep until its next timer instead of calling
  main_loop again at once (~115 times per 10 ms tick in a Chromium worker):
  an idle nginx pod 89 -> 20 ms CPU per second.
- **Saved VM states** (`web/src/vmstate.js`, stage 0 in
  `vm/init/init.c`): init waits in an initramfs for the pod; the first VM
  per memory size saves its state there, later pods restore it (~0.6 s less
  per start). After a restore,
  init must set the clock and reseed the RNG (else all pods share the random
  numbers), and v86 needs `preserve_mac_from_state_image` (else the network
  adapter has the wrong MAC and port-forward hangs). v86 0.5.473 zeroed all
  guest RAM on restore (160 ms and 240 MiB more RSS per pod); the fork skips
  that for fresh memory, so the `fastUnpack` override is gone. Kernel
  options that cost boot time: legacy PTYs (310 ms), gzip (LZ4 unpacks in
  a third of the time, in-guest zstd is 200 ms slower than LZ4); now the
  kernel ships unpacked (next point).
- **JIT modules of the kernel** (`web/src/jit.js`, `web/jit.mjs`, since
  2026-11-14): every pod restores the same state, so the kernel has the same
  code at the same physical pages in every pod, but each pod starts with an
  empty JIT, and the kernel (55 % of the instructions of an nginx start)
  ran in the interpreter. The web task records a generic busybox start in
  Node.js (Alpine linux/386 from docker, `JIT_ROOT_IMAGE`) and writes the
  50 most entered kernel modules to `dist/jit.bin` (1.2 MB, 0.18 MB
  gzip). The page passes it as `data-vm-jit` (the shortcode of the blog
  needs it); the tab compiles and warms it once at the prompt
  (`prefetchJIT`, `warm` in `jit.js`, see the next point), posts it with
  the start message, and the worker installs it after the restore
  (`jit_import` of the fork, 2-5 ms). The file names its build (the ID of
  the saved states: v86 version, kernel, init); v86 also checks its layout
  and the bytes of every page, so a mismatch installs nothing. Measured
  2026-11-14 in Node.js (v86 0.5.90-fork, nginx and the Go binary of
  pod-bench, 4 alternating runs of 3 pods per process): nginx, the first
  pod of a process: wall 626 -> 657 ms, main thread 601 -> 512 ms, process
  CPU 1.27 -> 1.71 s (V8 optimises the modules then, once per tab); every
  later pod: wall 566 -> 465 ms, main thread 556 -> 444 ms, process 805 ->
  755 ms. The Go binary to its first answer: 505 -> 535 ms first, 501 ->
  448 ms later. More modules make the first pod slower and the later ones
  faster (`web/jit.mjs`); headless Chromium showed the same.
- **Warm the kernel JIT modules at the prompt** (`warm` in
  `web/src/jit.js`, 2026-11-14): without it, V8 optimised the 50 modules
  with TurboFan during the first pod of a tab (~0.8 s of CPU on other
  threads). V8 tiers a wasm function up when its budget is used up, and
  only normal returns and loop back edges count (a call that throws does
  not). With a scratch memory that holds the statics of v86.wasm, a module
  reads zeroes as the TLB, bails at its first memory access and returns:
  50 x 3000 calls (~40 ms) tier all 50 up (1000 calls: 47). The optimised
  code stays with the Module that the tab posts to its pods
  (`--trace-wasm-compilation-times`: 50 TurboFan compiles before the first
  pod, none in the pods). The scratch memory had 64 pages before: the
  modules read statics up to ~17 MiB, and in the headless Chromium of the
  sandbox any wasm out-of-bounds trap crashed the renderer, the real page
  too. When: at the prompt. Started at page load (with the control plane
  boot), it made the prompt of a reload later (10 rounds: 6188 -> 6538
  ms); at the prompt it did not (6305 ms, noise). Measured in headless
  Chromium with the real page (8 alternating rounds, nginx, `kubectl run`
  -> HTTP; cold: new profile, image pulled from a local stand-in;
  return: same profile, new browser), none / modules without warm-up /
  with warm-up: run 3 s after the prompt (a person types): first pod cold
  2344 / 2326 / 2253 ms, return 1155 / 1214 / 1033 ms; later pods 724-765 /
  640-647 / 624-650 ms. `kubectl run` at the very prompt (22-27 runs
  pooled): first pod cold 5092 / 4913 / 5076 ms, return 2921 / 2873 /
  3002 ms, within the noise; the control plane is busy then (run -> start
  of the VM ~1.8 s), and the warm-up shares the CPU with it.
- Parked (2026-11-14): booting the VM of the first pod ahead in the tab
  (like the spare worker of `vm.js`). At page load it made the prompt of
  a reload later (6188 -> 6541 ms). At the prompt the VM part of the first
  pod got faster (start -> HTTP 1132 -> 964 ms), but with `kubectl run` at
  the very prompt the whole first pod not (2978 -> 3139 ms, 6 rounds), it
  competes with the control plane.
- **Direct kernel boot, no SeaBIOS** (`web/src/kernelboot.js`, since
  2026-11-12): the worker loads the segments of `vmlinux` (ELF, stripped),
  the initramfs and the zero page (E820, cmdline, initrd) into the VM and
  sets the CPU to `startup_32` in flat protected mode, like Firecracker.
  Without a BIOS, Linux finds no PCI routing table: `routePCI` programs the
  PIIX3 PIRQs (10, 10, 11, 11), the interrupt lines and the ELCR like
  SeaBIOS, else virtio fails with "can't find IRQ for PCI INT A". Measured
  in Node.js, run() to init `ready`, 3 x 6 rounds (medians): SeaBIOS +
  bzImage ~300 ms (256 MiB) / ~400 ms (2 GiB), a bzImage without BIOS the
  same, `vmlinux` ~280 / ~330 ms. So the BIOS was cheap; unpacking the
  kernel on the emulated CPU was not. The worker also boots in the VM it
  made for the state instead of a second one (`new V86` ~40 ms). In
  headless Chromium, start to `started` of a pod without a saved state
  (image present, 3 x 7 rounds): ~975 -> ~915 ms. Only the
  first boot per memory size gains; restoring a state and nginx after `go`
  did not change. Side effects: the state is 15.8 instead of 17.1 MiB, and
  the guest gets 16 MiB more RAM (SeaBIOS reserved the top 16 MiB). GitHub
  Pages gzips `vmlinux` (5.6 MB, 2 MB gzip).
  v86 saves all VGA memory in a state: pods use the smallest size (256 KiB
  instead of 8 MiB), which halves every state (15.8 -> 7.6 MiB).
- **Kernel config trimmed** (2026-11-12): other CPU vendors, PCI quirks and
  PCI serial cards, PTP, ethtool netlink, wireless, the crypto API, legacy
  virtio and a 4 KiB log buffer are off. `vmlinux` 5.6 -> 4.7 MB (gzip
  1.97 -> 1.81 MB), -10 % emulated instructions to "ready", +876 KiB free
  memory per pod; the boot time gain is below the noise (~50 ms). Most boot
  time is the JIT on cold kernel code, not idle waits. Keep PCI
  configuration type 1 (direct boot needs it).
- **Work before the save, not after `go`** (2026-11-12): what does not
  depend on the pod happens in stage 0, so the saved state has it done.
  Stage 0 brings up `lo` and `eth0` (eth0 fills its receive queue of 1024
  buffers: 0.8 million instructions) and mounts `/dev` (with `/dev/pts`,
  `/dev/shm` and the links), `/proc` and `/sys`; after `go` it moves them
  into the 9p root (`MS_MOVE`). init reads the config once, and the page puts
  `/etc/hosts` and `/etc/resolv.conf` into the tree instead of init writing
  them over 9p. An empty `$PIR` table at 0xf0000 (`kernelboot.js`) ends the
  search of Linux for a BIOS routing table (0.4 million instructions per
  boot). The kernel is built with `-O2`: -5 % instructions, and v86 runs
  that code faster. Measured in Node.js (256 MiB): `go` to `started`
  2.35 -> 0.94 million instructions, ~100 -> ~40 ms; nginx from `go` to
  HTTP ~2.2 -> ~1.95 s (3 x 4 rounds); boot to `ready` 11.1 -> 11.4
  million instructions (once per memory size); state 7.6 -> 8.4 MiB.
- **Where the instructions go now** (Node.js profile, 256 MiB): boot to
  `ready` is memory init (~19 %, grows with the RAM), alternatives
  patching (~9 %), sysfs, kobjects and uevents (~15 %), printk into the log
  buffer even with `quiet` (~6 %) and the random IP IDs of `ip_rt_init`
  (~5 %). None has a Kconfig switch (`DEFERRED_STRUCT_PAGE_INIT` is 64-bit
  only). nginx from `go` to HTTP is ~58 million instructions: ~37 % user
  code, page faults ~15 %, system calls ~18 %; init is ~2 % of it. 9p has
  a request in flight for only ~10 % of the time. v86 runs ~25-35 million
  instructions per second here, so instructions are time.
- **Node join over WebRTC** with copy and paste signaling and STUN, one UDP mux per
  node. The node runs without `--privileged`: the agent re-execs into
  user/mount/net/cgroup namespaces, pasta (built from passt.top at the fixed
  commit `6aa4f88`, no Renovate on purpose) for the network,
  `KubeletInUserNamespace`. Keep `VOLUME /var/lib/containerd`.
  A `--tmpfs` variant for containerd was discussed and not wanted.
- **Paired nodes** (`join --keep`, 2026-11-12): signaling through an ntfy
  relay (`https://ntfy.sh` by default, it sends CORS), sealed with AES-GCM
  and a key per node, so a node on a server needs no open port and comes
  back after a reload. Chosen over an HTTPS endpoint in the agent (every
  visitor would need a reachable URL with TLS). The pairing is a Secret in
  kube-system; `dropNode` and `dropOldNodes` skip paired nodes. After a
  hibernation the worker calls `restoreNode` again: the old `open`
  functions are dead stand-ins. Tested with a fake ntfy (POST, `/json`,
  `/sse`, `since=`) and the agent with `--no-kubelet`; a sealed offer is
  ~700 bytes (ntfy.sh takes 4096). `join --kubectl` uses the same pairing
  (kind `kubectl`, no node, no IP) for a kubectl outside the browser; the
  agent prints the kubeconfig on stdout and logs on stderr, on Joe's wish.
  Tested with a real kubectl v1.37.2 (get, create, auth whoami, after a
  reload).
- **Persistence**: image layers in OPFS (`web/src/layers.js`, served to v86
  over 9p), cluster as an etcd snapshot in IndexedDB (`state.go`,
  `etcdshim/snapshot.go`), files of `/root` in IndexedDB, saved VM states
  in OPFS. `forget` deletes all of it.
- **Build tooling is mise** (`mise.toml` tasks), not a Makefile.
- **Terminal**: the shell is mvdan.cc/sh with Go built-ins (coreutils, `wget`,
  `vi`, `kubectl edit` in raw mode). busybox-wasm and vigo were tried and
  rejected.
- **Go heap snapshot** (`k8s/snapshot.mjs`, run by `k8s/build.sh`): Node.js
  runs the binary until `main` sleeps (`tabernetesSnapshot`), and the memory
  and Wasm globals become the data and globals of the shipped binary.
  `runGo` in `web/src/wasm.js` rebuilds the JavaScript values that Go holds
  (8, all found by name: `Object`, `fs`, ...) and resumes. Saves ~0.9 s of
  package init per Go start (0.4 s init, 0.5 s lazy compile of init code),
  +0.6 MB zst. The build fails if init leaves a value that cannot be found
  by name or an open file. The env and `fs.constants` of the page must
  match the build (checked at start). All starts share the random state of
  the build: `main` reseeds `util/rand`; map order and `math/rand` repeat,
  `crypto/rand` does not. The sleep must be long (100 ms): with 1 ms, work
  left over from init lets the timer expire and Go never pauses. In-process
  reloads gain less, Chrome reuses the compiled code of the same bytes.
- **Hibernation** (`web/src/hibernate.js`, `cluster.js`): when the last tab
  closes, the worker copies memory, Wasm globals (the build exports them as
  `g<i>`), the fs and `go._values` in one JavaScript task, gzips the memory
  (~360 MiB -> ~40 MB, ~5 s, CompressionStream) and puts it into IndexedDB
  (`cluster` store, key `hibernated`). The next worker takes it (read and
  delete), unpacks it while the tab sends the binary, and resumes instead of
  `runGo`: prompt ~3.4 s instead of ~9 s (Chromium, 2026-11-12). Measured
  stable over 8 chained resumes and after a faked 30 h and 60 h gap.
  Rules: the image matches only its build (`build` in the snapshot section);
  a joining tab voids it; the etcd saves pause while hibernated; a failed
  resume does not drop the etcd snapshot. Stand-ins of tab objects must stay
  recognisable (`standIns`): a Proxy looked like a plain object to the next
  capture, and the second resume of a chain crashed on `postMessage`. On
  resume the stand-ins' Go handlers get `onmessage({data: null})` and
  `onclose()`, which ends the goroutines of the old tabs. Tab numbers are
  the lowest free ones (tabs.go), else a hibernated cluster counts up
  forever. Firefox and Safari end the worker with the last tab: no image.
- **poweroff, shutdown, reboot** (`terminal.js`, `cluster.js`): stop the
  control plane of every tab. The worker broadcasts a wall(1)-like message,
  the tabs end their pods, and the worker runs `forget` (cluster, `/root`,
  images, VM states) and closes like after a crash. Joe wants a wiped
  cluster, like on the first visit, not a kept one (2026-11-12). reboot
  then boots a new cluster in the same tab,
  in place (`restart` in `index.js`), not by a reload: the blog page sits
  behind a start button. The other tabs stay down until Enter. The tabs end
  the workers of their pods and close their WebRTC connections, so Docker
  nodes end too. Without a SharedWorker, poweroff and reboot reload the page.
- **Image pulls** download and unpack up to 3 layers at once, like
  containerd's `max_concurrent_downloads`. On a fast link the browser is
  CPU bound (gunzip, SHA-256, OPFS) and gains little; it saves round trips
  through the mirror.
- **kubectl translations are off** (patch.go): loading them zipped and parsed
  the `.po` files during init (~0.1 s), and the terminal sets no `LANG`.
- **Persistence rules**: the etcd snapshot is saved only after boot, and a
  change of lease keys alone does not trigger a save. A snapshot of another
  Kubernetes minor version, or one that fails to boot, is dropped. `forget`
  keeps the layers of running pods with a `<digest>.forgotten` mark; page
  load and image GC sweep them later.

## Hosting and network constraints

- **No registry sends CORS headers** (Docker Hub incl. auth and CDN, ghcr.io,
  quay.io, public.ecr.aws, mirror.gcr.io, registry.gitlab.com). There is no
  browser trick around it (`no-cors` is opaque). Tab pods pull through Joe's
  Docker Hub pull-through mirror `https://tabernetes.oracle.jkroepke.de`
  (`registry:3` + a CORS middleware, GET/HEAD only). Its deployment files are
  private and must not be committed. Hugging Face sends CORS, so WebLLM
  weights load directly.
- **GitHub Pages** cannot set headers: no `Content-Encoding: zstd`, no
  COOP/COEP, only `max-age=600`, and its CDN gzips the `.zst` again (so
  `Content-Length` is useless for progress; the page gets the exact size from
  the shortcode). Hence the binary is shipped as 32 MiB zstd frames and
  decoded in workers with zstddec (zstd in Wasm, 2.5x faster than fzstd,
  which `layers.js` still uses for streamed layers); Chromium's
  `DecompressionStream` has no zstd. ghcr.io answers the CORS preflight with 405, so OCI artifacts are no
  option for the binary either.
- The blog's CSP adds `'wasm-unsafe-eval'` only on pages with the shortcode.
- Native `Content-Encoding: zstd` would need a proxy in front of Pages (for
  example Cloudflare). Not wanted: the zstd frames already decode in
  parallel with download and compile.

## Runtime gotchas (Go `js/wasm` and browsers)

- No preemption in Wasm: busy loops starve everything (APF ensurer needed a
  sleep); calling JS from a goroutine during apiserver boot is delayed by
  seconds, so invoke synchronously.
- `runtime.MemProfileRate = 0` and `debug.SetMemoryLimit(3 GiB)` are required:
  memory profiling crashed with "invalid runtime symbol table" when unwinding
  from `runtime.beforeIdle`.
- RSA key generation is too slow: certificates use ECDSA (patch in client-go).
- Go's wall clock in `wasm_exec.js` uses `Date.now()` (milliseconds);
  client-go event names use `UnixNano`, so two events in the same
  millisecond collide. The web task of `mise.toml` patches it to use
  `performance.now()` while that agrees with `Date.now()`. The tab node still
  records events through a queue, one per millisecond, because Firefox and
  Safari coarsen `performance.now()` to about 1 ms.
- SharedWorker: no nested Worker, no `RTCPeerConnection`, a
  `WebAssembly.Module` cannot be posted (messageerror). A teed ReadableStream
  can be transferred. WebRTC therefore lives in the tabs and is bridged to the
  worker.
- Wasm tests need `env -i` (else "command line and environment variables
  exceeds limit").
- Pod proxy through the apiserver (`/proxy/`) fails in Wasm; port-forward
  works. SPDY dialer gives EOF in Wasm, use the websocket dialer.
- Lock pitfalls in the OPFS layer store: never delete only the `.json` index
  of a used layer (a re-unpack truncates the tar a pod reads), never queue an
  exclusive Web Lock request on a layer (it blocks new shared requests), use
  `ifAvailable`.
- v86 VM: tty sends `\r\n` on ttyS1; init must never power off (no ACPI, it
  blocks and the page kills the worker); glibc images need
  `CONFIG_COMPAT_32BIT_TIME`, `/dev/stdout`, `/dev/stderr` and `/dev/fd`.
  Always test with a glibc image (`nginx`), not only Alpine. A fresh nginx
  refuses connections for 1-3 s after Ready. The guest must send a packet
  first (ping the router) so the network adapter learns its MAC.
- v86 names the 9p device `host9p` and answers statfs with 256 GiB and the
  size of the image as used. `kernelboot.js` renames the device to
  `overlay` before boot (init mounts it by that name, so a saved state of
  an older init does not fit) and `statRoot` (`rootfs.js`) reports the
  ephemeral-storage limit or the image file system as the size, and the
  files of the pod as used. v86 does not enforce that size.
- v86 sends qid version 0 for every file, and Linux 9p then opens the file
  without the page cache: every read() was a 9p request. init mounts with
  `ignoreqv` (2026-11-14): glibc text tools -17 % CPU, 9p reads 9900 ->
  2100. Linux allocated, zeroed and mapped a readdir buffer of msize for
  every directory: `vm/kernel-patches/9p-readdir-buffer.patch` caps it at
  16 KiB (glibc text tools -3.3 % CPU). `vm/Dockerfile` applies the files
  of `vm/kernel-patches`; a new kernel version may need them updated.
  Measured without gain: msize 64/128/512 KiB (256 KiB is best), `cache=mmap`,
  a smaller readahead, large folios for 9p with 64 KiB exec folios,
  fault_around_bytes 16 KiB.

## Node gotchas

- containerd registry pulls are HTTP/1.1 only. Pulls stalled on Docker
  Desktop/WSL2 (bytes stop arriving in the netns; not pasta, not containerd).
  Mitigations in place: `use_local_image_pull = true`, pull progress timeout
  20 s, and preloaded system images in the node image (an OCI layout served by
  `node/agent/imagemirror.go`). To debug a hang: `kill -USR1` containerd via
  `/proc` (the image has no `kill`/procps) and read the goroutine dump in
  `/var/log/containerd.log`; the agent restarts a killed containerd.
- What the stall investigation (2026-11-08) proved, so nobody repeats it:
  the goroutine dump showed a fetch blocked in a TLS read for 13 min, so no
  bytes reached the netns. A newer pasta and a CONNECT proxy with a native
  socket (tried, then reverted) both still stalled, so pasta is not the cause.
  pasta answers TCP keepalives locally, so a dead upstream connection never
  dies; only the timeout helps. The CRI transfer service counts a layer as
  active only after its first progress, so the plain progress timeout did
  not fire; `use_local_image_pull` counts every HTTP request. 20 s, not 10 s,
  because of TCP retransmit backoff. `serializeImagePulls` stays `false`:
  serial pulls plus back-off made the start take ~3 min. Parked alternatives:
  Netavark (Podman only), RootlessKit (same as `userns.go`),
  gvisor-tap-vsock, bypass4netns.
- LAN join: publish the UDP port on all interfaces and pass
  `--advertise <LAN IP>` (the browser hides its IPs behind mDNS).

## Testing without the maintainer's hosts

- Build the Wasm binary without mise: export `KUBERNETES_VERSION` and
  `MVDAN_SH_VERSION` from `mise.toml`, `go -C k8s run . $PWD/.build/kubernetes`,
  then `k8s/build.sh .build/kubernetes .build/tabernetes.wasm` (~4 min).
- Browser tests: serve `dist/` with a small static server plus a Docker Hub
  CORS stand-in (token from auth.docker.io), drive `tabernetes.shell` and
  `tabernetesTerminal.exec` with Playwright in headless Chromium. Playwright
  cannot evaluate in the SharedWorker; use CDP (`--remote-debugging-port`,
  `/json/list`, `Runtime.evaluate`) to crash or inspect it. Write test output
  to a file; piping through `tail` hangs because the server keeps the pipe
  open.
- Kernel builds: `LLVM=1 ARCH=i386`. Sandboxes may block kernel.org and the
  tarballs of GitHub, but a Git fetch of `gregkh/linux` (what `ADD ...git` in
  `vm/Dockerfile` does) usually works. Delete the tree afterwards; sandbox
  disks are small.
- Boot test: `vm/test/boot.test.mjs` boots `dist/vm` in v86 in Node.js, saves
  and restores the VM and starts a tiny ELF as the pod. `TABERNETES_VM` points
  it at another directory. For a real image, export a `linux/386` image
  (`docker export`) into a `Tree` with the files in memory; nginx (Debian)
  answered HTTP on 7.3.4.
- Measure performance in several rounds: run-to-run variance is about one
  second.
- Count instructions of the VM with `emulator.get_instruction_counter()`;
  a listener on `serial1-output-byte` reads it at the exact instruction, so
  `report()` lines in init work as probes. For a profile, build the kernel
  with `CONFIG_UNWINDER_FRAME_POINTER=y`, sample `cpu.instruction_pointer`
  between v86 ticks and walk the EBP chain in `cpu.mem8` (the virtual
  address minus 0xc0000000) against `System.map`. A tick often ends at an interrupt:
  then `[esp]` is the interrupted EIP, and an ESP of 0xffc0xxxx (the entry
  stack) means user mode.
- Crash the control plane on purpose: CDP `Runtime.evaluate` of
  `globalThis.tabernetes.attachPort(null,'api')` in the SharedWorker. Test
  image GC with a vmworker bundle built with a small `IMAGE_FS` budget.
- Sandboxes may refuse to build code fetched from outside (forks of v86,
  kernel trees from GitHub), and their proxy may block demo sites on
  github.io or pages.dev. Ubuntu packages over apt usually work, and dockerd
  can be started by hand.

## Parked ideas (do not reopen without new numbers)

- **Pod kernel knobs without gain** (2026-11-12, Node.js): `INIT_STACK_NONE`
  (-0.5 % instructions), smaller hash tables on the command line
  (`thash_entries`, `dhash_entries`, ...), `lpj=`, `nopti`. `PREEMPT_NONE`
  and `PREEMPT_VOLUNTARY` do not exist for x86 anymore (lazy preemption).
  `PRINTK=n` would save ~6 % of the first boot, but pods would lose kernel
  messages (OOM kills, segfaults) in their log.
- **Splitting the control plane into more workers** (apiserver / controllers /
  kubelet roles of one binary): measured on 2026-11-11, no gain beyond noise,
  +150 MiB per tab. Parked.
  A kubelet-only variant first looked faster, but the early prompt came from a
  bug (ready before the default ServiceAccount existed). Two rounds were not
  enough to see that.
- **Trimming controllers or APIs**: rejected (-0.4 s boot only).
  The `providerless` build tag of k0s/k3s is a no-op in v1.37.
- **wasm-opt -Oz**: -0.6 % zst, no faster boot. Rejected.
- **`GOWASM=satconv,signext`**: no-op, Go 1.27 always emits both.
- **Eager Wasm compile** (no lazy compile): 2.9 s instead of 0.4 s.
- **Leader/follower etcd replication between tabs**: moot with the
  SharedWorker.
- **64-bit images (x86_64, arm64) via QEMU-wasm** (ktock/qemu-wasm, Wasm TCG
  backend, needs SharedArrayBuffer via coi-serviceworker): a POC worked
  (x86_64 nginx:alpine HTTP-ready ~28 s, arm64 ~14 s, v86 i386 3-4 s; Wasm
  ~3.4-4.7 MB gzip; ~2.2 GiB RSS per pod). SeaBIOS needs `qboot.rom`, x86 needs
  `no_timer_check`, the pty poll must not block. Revisit when the Wasm TCG
  backend lands upstream, then pick the emulator per image architecture
  (386 -> v86, else QEMU). riscv64 via TinyEMU was rejected (no JIT).
  ktock/qemu-wasm runs on wasm32 (wasm64 is not needed); the arm64 prebuilt
  prints zero-padded numbers empty.
- **v86 forks for 64-bit** (reviewed 2026-11-11): both keep the v86 API that
  Tabernetes uses. v86_64 is x86_64 only, 1 CPU, 64-bit JIT, wasm32 up to
  4 GiB. v64 does x86 32/64 and ARM64 (up to 8 cores with COOP/COEP), but its
  ARM64 `virt` board has no virtio-9p, so the 9p layer rootfs does not work
  there without a port to virtio-mmio/pci.
  Measured with the pod setup (9p rootfs, fetch network, Go init, 512 MiB,
  1 CPU, Node.js, x86_64 tinyconfig kernel = `vm/kernel.config` without the
  i386 options): nginx answered HTTP after 2.5-2.9 s on v86 (386) and after
  7.0-8.0 s on v64 (x86_64), with Alpine and Debian alike. Inside a running
  pod, v64 is only 0-30 % slower (gzip, sha256, a shell loop); the gap is
  boot. v64 needs `cpu_type: "x86_64"` and `graphics_adapter: "bochs_vga"`
  (`"none"` crashes in SeaBIOS) and is not on npm. v86_64 (c394574) cannot run
  Go: every amd64 Go binary, our init too, dies in `mallocinit` with
  "sysMemStat overflow", with and without the JIT. Next step if 64-bit is
  wanted: v64 for images without a `386` variant, v86 for the rest.
- Of 37 popular Docker Hub images, 19 have `linux/386`, 24 `riscv64`, 12
  neither (node, MySQL, mariadb, mongo, rabbitmq, grafana, ...).
