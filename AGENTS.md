# AGENTS.md

Guidance for coding agents (and humans) that work on Tabernetes. The
[Readme](README.md) explains what Tabernetes is and how it works; this file
holds the decisions, constraints and gotchas behind it that are not obvious
from the code. Read both before you change something.

Tabernetes ("Kubernetes in your tab") is a real Kubernetes control plane
(kube-apiserver, kube-controller-manager, kube-scheduler, kubectl) compiled
to `js/wasm` and running in a browser tab, plus a Docker node image that joins
the cluster over WebRTC. It is the demo on <https://jkroepke.de/tabernetes/>.
It was called "kwasm" until 2026-11-08; old commits, branches and notes use
that name.

## Repository and release

- Tabernetes lived in `tabernetes/` (before that `kwasm/`) of
  [jkroepke/blog](https://github.com/jkroepke/blog). The history up to
  `jkroepke/blog#154` was imported with `git filter-repo`, so `#123` in old
  commit messages was rewritten to `jkroepke/blog#123`.
- The blog does not build Tabernetes anymore. It pins a release
  (`TABERNETES_VERSION` in the `mise.toml` of the blog, bumped by Renovate),
  downloads `tabernetes.tar.gz`, verifies its attestation, unpacks it into
  `assets/tabernetes/` and serves `proxy-sw.js` as `/tabernetes-proxy/sw.js`.
  The shortcode `layouts/_shortcodes/tabernetes.html` and the page
  `content/tabernetes/index.md` stay in the blog. A change of the `data-*`
  contract of `web/src/index.js` therefore needs a change of the shortcode in
  the blog after the release.
- Releases: semantic-release (`.releaserc.json`, commit analyzer only) runs on
  every push to `main` and creates the tag with `GITHUB_TOKEN`, then dispatches
  CI on the tag (a tag pushed with `GITHUB_TOKEN` triggers no workflow, a
  `workflow_dispatch` does; no GitHub App needed); the tag run of CI builds,
  pushes the node image as `<version>` and `latest`, attests and publishes the
  release. PR titles must start with `feat`, `fix`, `chore` or `docs`
  (`pr-check.yaml`); squash merges make the PR title the commit message.
- The release job runs only when the repository variable `RELEASES_ENABLED`
  is `true`. Set it to anything else to merge to `main` without releasing.
- The node image of a release is pinned in the bundle (`TABERNETES_VERSION`
  at build time). Local builds and PRs use `latest`.

## Working rules of the maintainer

- Agents may push to this repository directly; commits here do not need
  Joe's GPG/SSH signature. Only the blog needs signed commits made on Joe's
  Mac.
- No references to Claude or AI in commit messages or PR bodies. The GitHub
  tooling may append a "Generated by Claude Code" footer to a PR body; remove
  it after creating the PR.
- Sign off every commit for the DCO (`git commit -s`), in this repository and
  in the blog.
- Ask before a force push.
- Write docs and comments in plain English (B2 level): short sentences that
  explain the why.

## Architecture decisions (and why)

- **Upstream components, no simulators.** The maintainer wants the normal
  Kubernetes experience. When a tab feature prints events or status, copy the
  upstream kubelet messages (`Pulling`, `Successfully pulled ... Image size`,
  `already present on machine`, `ErrImagePull`, `ImagePullBackOff`, ...) from
  the Kubernetes source instead of inventing text. Readers should recognise
  real kubectl output.
- **One binary.** apiserver, controller-manager, scheduler, kubectl, the shell
  (mvdan.cc/sh) and an in-memory etcd v3 gRPC shim (`k8s/tabernetes/etcdshim`).
  Go `js/wasm` has an in-process fake network (`net.Listen`/`net.Dial` match
  the exact address), so the components talk to each other unchanged. Bind to
  `127.0.0.1`, never `0.0.0.0`.
- **Control plane in a SharedWorker** (`web/src/cluster.js`,
  `k8s/tabernetes/tabs.go`). Every tab joins as node `tab-N` over
  MessagePorts; a Web Lock per tab is its liveness. A closed tab is taken over
  by the others (the `llm` Deployment prefers its tab but is not pinned).
  Without SharedWorker or Web Locks the tab runs the control plane itself.
  Chrome on Android has SharedWorker again since Chrome 148. The worker is
  created with `extendedLifetime` (Chrome 148+), so it outlives the last tab
  by about 30 s and a reload joins the running cluster (2-3 s to the prompt
  instead of ~12 s). `forget` closes it with the last tab.
- **The kubelet of a tab is like a Virtual Kubelet**: a node for the control
  plane, but no container runtime. Limit of 8 pods per tab (kept on purpose).
- **Real images in a tab run in v86** (32-bit x86 JIT to Wasm, npm `v86`),
  one worker per pod, `linux/386` image variants. Chosen over TinyEMU (no JIT,
  last release 2019). Kernel: Linux 6.8 i386 `tinyconfig` + `vm/kernel.config`
  with `CONFIG_HIGHMEM4G` (pods up to 2 GiB; v86 caps guest RAM at
  2 GiB - 128 KiB; without highmem the guest used only ~896 MiB).
- **PID 1 of the VM is C** (`vm/init/init.c`, static, musl, compiled by
  `zig cc -target x86-linux-musl` from pip in `vm/Dockerfile`; an i386
  Alpine fails on the arm64 CI runners). It was Go until 2026-11-11. Measured
  with the same pod: 77 KB instead of 3.1 MB, 0.2 MiB RSS and 1 thread
  instead of 3.7 MiB and 5, a saved VM state of 17.9 instead of 23.7 MB, and
  the pod starts ~80 ms sooner in the browser. Idle CPU did not change on
  the tickless kernel (Go's sysmon sleeps when nothing runs). Keep it one
  poll loop without threads, and keep the exec protocol of
  `k8s/tabernetes/v86exec.go`. `vm/test` runs init on the host
  (`TABERNETES_INIT_TEST`, no mounts, Linux only) and checks exec, attach,
  stdin acks, ttys and exit codes.
- **Saved VM states** (`web/src/vmstate.js`, stage 0 in
  `vm/init/init.c`): init waits in an initramfs for the pod; the first VM
  per memory size saves its state there, later pods restore it (~0.6 s less
  per start). After a restore,
  init must set the clock and reseed the RNG (else all pods share the random
  numbers), and v86 needs `preserve_mac_from_state_image` (else the network
  adapter has the wrong MAC and port-forward hangs). `fastUnpack` replaces
  v86's `unpack_memory`, which zeroed all guest RAM (160 ms and 240 MiB more
  RSS per pod). Kernel options that cost boot time: legacy PTYs (310 ms),
  gzip (LZ4 unpacks in a third of the time, in-guest zstd is 200 ms slower
  than LZ4).
- **Node join over WebRTC** with copy and paste signaling and STUN, one UDP mux per
  node. The node runs without `--privileged`: the agent re-execs into
  user/mount/net/cgroup namespaces, pasta (built from passt.top at the fixed
  commit `6aa4f88`, no Renovate on purpose) for the network,
  `KubeletInUserNamespace`. Keep `VOLUME /var/lib/containerd`.
  A `--tmpfs` variant for containerd was discussed and not wanted.
- **Persistence**: image layers in OPFS (`web/src/layers.js`, served to v86
  over 9p), cluster as an etcd snapshot in IndexedDB (`state.go`,
  `etcdshim/snapshot.go`), files of `/root` in IndexedDB, saved VM states
  in OPFS. `forget` deletes all of it.
- **Build tooling is mise** (`mise.toml` tasks), not a Makefile.
- **Terminal**: the shell is mvdan.cc/sh with Go built-ins (coreutils, `wget`,
  `vi`, `kubectl edit` in raw mode). busybox-wasm and vigo were tried and
  rejected.
- **Persistence rules**: the etcd snapshot is saved only after boot, and a
  change of lease keys alone does not trigger a save. A snapshot of another
  Kubernetes minor version, or one that fails to boot, is dropped. `forget`
  keeps the layers of running pods with a `<digest>.forgotten` mark; page
  load and image GC sweep them later.

## Hosting and network constraints

- **No registry sends CORS headers** (Docker Hub incl. auth and CDN, ghcr.io,
  quay.io, public.ecr.aws, mirror.gcr.io, registry.gitlab.com). There is no
  browser trick around it (`no-cors` is opaque). Tab pods pull through Joe's
  Docker Hub pull-through mirror `https://tabernetes.oracle.jkroepke.de`
  (`registry:3` + a CORS middleware, GET/HEAD only). Its deployment files are
  private and must not be committed. Hugging Face sends CORS, so WebLLM
  weights load directly.
- **GitHub Pages** cannot set headers: no `Content-Encoding: zstd`, no
  COOP/COEP, only `max-age=600`, and its CDN gzips the `.zst` again (so
  `Content-Length` is useless for progress; the page gets the exact size from
  the shortcode). Hence the binary is shipped as 32 MiB zstd frames and
  decoded in a worker with fzstd; Chromium's `DecompressionStream` has no
  zstd. ghcr.io answers the CORS preflight with 405, so OCI artifacts are no
  option for the binary either.
- The blog's CSP adds `'wasm-unsafe-eval'` only on pages with the shortcode.
- Native `Content-Encoding: zstd` would need a proxy in front of Pages (for
  example Cloudflare). Not wanted: the fzstd frames already decode in
  parallel with download and compile.

## Runtime gotchas (Go `js/wasm` and browsers)

- No preemption in Wasm: busy loops starve everything (APF ensurer needed a
  sleep); calling JS from a goroutine during apiserver boot is delayed by
  seconds, so invoke synchronously.
- `runtime.MemProfileRate = 0` and `debug.SetMemoryLimit(3 GiB)` are required:
  memory profiling crashed with "invalid runtime symbol table" when unwinding
  from `runtime.beforeIdle`.
- RSA key generation is too slow: certificates use ECDSA (patch in client-go).
- Go's wall clock in `wasm_exec.js` uses `Date.now()` (milliseconds);
  client-go event names use `UnixNano`, so two events in the same
  millisecond collide. The web task of `mise.toml` patches it to use
  `performance.now()` while that agrees with `Date.now()`. The tab node still
  records events through a queue, one per millisecond, because Firefox and
  Safari coarsen `performance.now()` to about 1 ms.
- SharedWorker: no nested Worker, no `RTCPeerConnection`, a
  `WebAssembly.Module` cannot be posted (messageerror). A teed ReadableStream
  can be transferred. WebRTC therefore lives in the tabs and is bridged to the
  worker.
- Wasm tests need `env -i` (else "command line and environment variables
  exceeds limit").
- Pod proxy through the apiserver (`/proxy/`) fails in Wasm; port-forward
  works. SPDY dialer gives EOF in Wasm, use the websocket dialer.
- Lock pitfalls in the OPFS layer store: never delete only the `.json` index
  of a used layer (a re-unpack truncates the tar a pod reads), never queue an
  exclusive Web Lock request on a layer (it blocks new shared requests), use
  `ifAvailable`.
- v86 VM: tty sends `\r\n` on ttyS1; init must never power off (no ACPI, it
  blocks and the page kills the worker); glibc images need
  `CONFIG_COMPAT_32BIT_TIME`, `/dev/stdout`, `/dev/stderr` and `/dev/fd`.
  Always test with a glibc image (`nginx`), not only Alpine. A fresh nginx
  refuses connections for 1-3 s after Ready. The guest must send a packet
  first (ping the router) so the network adapter learns its MAC.

## Node gotchas

- containerd registry pulls are HTTP/1.1 only. Pulls stalled on Docker
  Desktop/WSL2 (bytes stop arriving in the netns; not pasta, not containerd).
  Mitigations in place: `use_local_image_pull = true`, pull progress timeout
  20 s, and preloaded system images in the node image (an OCI layout served by
  `node/agent/imagemirror.go`). To debug a hang: `kill -USR1` containerd via
  `/proc` (the image has no `kill`/procps) and read the goroutine dump in
  `/var/log/containerd.log`; the agent restarts a killed containerd.
- What the stall investigation (2026-11-08) proved, so nobody repeats it:
  the goroutine dump showed a fetch blocked in a TLS read for 13 min, so no
  bytes reached the netns. A newer pasta and a CONNECT proxy with a native
  socket (tried, then reverted) both still stalled, so pasta is not the cause.
  pasta answers TCP keepalives locally, so a dead upstream connection never
  dies; only the timeout helps. The CRI transfer service counts a layer as
  active only after its first progress, so the plain progress timeout did
  not fire; `use_local_image_pull` counts every HTTP request. 20 s, not 10 s,
  because of TCP retransmit backoff. `serializeImagePulls` stays `false`:
  serial pulls plus back-off made the start take ~3 min. Parked alternatives:
  Netavark (Podman only), RootlessKit (same as `userns.go`),
  gvisor-tap-vsock, bypass4netns.
- LAN join: publish the UDP port on all interfaces and pass
  `--advertise <LAN IP>` (the browser hides its IPs behind mDNS).

## Testing without the maintainer's hosts

- Build the Wasm binary without mise: export `KUBERNETES_VERSION` and
  `MVDAN_SH_VERSION` from `mise.toml`, `go -C k8s run . $PWD/.build/kubernetes`,
  then `k8s/build.sh .build/kubernetes .build/tabernetes.wasm` (~4 min).
- Browser tests: serve `dist/` with a small static server plus a Docker Hub
  CORS stand-in (token from auth.docker.io), drive `tabernetes.shell` and
  `tabernetesTerminal.exec` with Playwright in headless Chromium. Playwright
  cannot evaluate in the SharedWorker; use CDP (`--remote-debugging-port`,
  `/json/list`, `Runtime.evaluate`) to crash or inspect it. Write test output
  to a file; piping through `tail` hangs because the server keeps the pipe
  open.
- Kernel builds: `LLVM=1 ARCH=i386` from Ubuntu `linux-source` (cloning kernel
  trees from GitHub may be blocked in sandboxes). Delete the tree afterwards;
  sandbox disks are small.
- Measure performance in several rounds: run-to-run variance is about one
  second.
- Crash the control plane on purpose: CDP `Runtime.evaluate` of
  `globalThis.tabernetes.attachPort(null,'api')` in the SharedWorker. Test
  image GC with a vmworker bundle built with a small `IMAGE_FS` budget.
- Sandboxes may refuse to build code fetched from outside (forks of v86,
  kernel trees from GitHub), and their proxy may block demo sites on
  github.io or pages.dev. Ubuntu packages over apt usually work, and dockerd
  can be started by hand.

## Parked ideas (do not reopen without new numbers)

- **Splitting the control plane into more workers** (apiserver / controllers /
  kubelet roles of one binary): measured on 2026-11-11, no gain beyond noise,
  +150 MiB per tab. Parked.
  A kubelet-only variant first looked faster, but the early prompt came from a
  bug (ready before the default ServiceAccount existed). Two rounds were not
  enough to see that.
- **Trimming controllers or APIs**: rejected (-0.4 s boot only).
  The `providerless` build tag of k0s/k3s is a no-op in v1.37.
- **wasm-opt -Oz**: -0.6 % zst, no faster boot. Rejected.
- **Leader/follower etcd replication between tabs**: moot with the
  SharedWorker.
- **64-bit images (x86_64, arm64) via QEMU-wasm** (ktock/qemu-wasm, Wasm TCG
  backend, needs SharedArrayBuffer via coi-serviceworker): a POC worked
  (x86_64 nginx:alpine HTTP-ready ~28 s, arm64 ~14 s, v86 i386 3-4 s; Wasm
  ~3.4-4.7 MB gzip; ~2.2 GiB RSS per pod). SeaBIOS needs `qboot.rom`, x86 needs
  `no_timer_check`, the pty poll must not block. Revisit when the Wasm TCG
  backend lands upstream, then pick the emulator per image architecture
  (386 -> v86, else QEMU). riscv64 via TinyEMU was rejected (no JIT).
  ktock/qemu-wasm runs on wasm32 (wasm64 is not needed); the arm64 prebuilt
  prints zero-padded numbers empty.
- **v86 forks for 64-bit** (reviewed 2026-11-11): both keep the v86 API that
  Tabernetes uses. v86_64 is x86_64 only, 1 CPU, 64-bit JIT, wasm32 up to
  4 GiB. v64 does x86 32/64 and ARM64 (up to 8 cores with COOP/COEP), but its
  ARM64 `virt` board has no virtio-9p, so the 9p layer rootfs does not work
  there without a port to virtio-mmio/pci.
  Measured with the pod setup (9p rootfs, fetch network, Go init, 512 MiB,
  1 CPU, Node.js, x86_64 tinyconfig kernel = `vm/kernel.config` without the
  i386 options): nginx answered HTTP after 2.5-2.9 s on v86 (386) and after
  7.0-8.0 s on v64 (x86_64), with Alpine and Debian alike. Inside a running
  pod, v64 is only 0-30 % slower (gzip, sha256, a shell loop); the gap is
  boot. v64 needs `cpu_type: "x86_64"` and `graphics_adapter: "bochs_vga"`
  (`"none"` crashes in SeaBIOS) and is not on npm. v86_64 (c394574) cannot run
  Go: every amd64 Go binary, our init too, dies in `mallocinit` with
  "sysMemStat overflow", with and without the JIT. Next step if 64-bit is
  wanted: v64 for images without a `386` variant, v86 for the rest.
- Of 37 popular Docker Hub images, 19 have `linux/386`, 24 `riscv64`, 12
  neither (node, MySQL, mariadb, mongo, rabbitmq, grafana, ...).
